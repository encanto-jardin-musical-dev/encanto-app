Datos y seguridad

La base de datos rechaza lo que no corresponde al rol

Cada tabla aplica RLS asociada al usuario autenticado — no es solo la interfaz, es la propia base de datos.

Acceso por rol

Una sola función, get_user_groups(user_id, user_role): un padre solo alcanza los grupos de sus hijos; un docente, solo los grupos que tiene asignados.

Refuerzo del 2026-09-09

Índices de cobertura en llaves foráneas, políticas RLS reescritas para no reevaluarse por fila, políticas permisivas consolidadas, permisos de funciones security-definer revocados.

✓ profiles · children · child_guardians · groups ✓ messages · daily_reports · attendance · tasks ✓ 4 buckets de storage, todos privados

El asesor de rendimiento marca 18 índices como "no usados" — esperable con el tráfico bajo actual, no una regresión.

Cierre

Demo en vivo

Recordatorio: mostrar aquí el recorrido padre → docente → administrador (feed, mensajería, reporte diario con foto, asistencia, una tarea, límite de permisos) antes de abrir a preguntas.
Antes de empezar
  • No usar las cuentas fixture de e2e (e2e-parent@encanto.test, etc.) — teardownFixtures() las borra en cada corrida. Usar un set de datos de staging estable.
  • Tener 3 perfiles/pestañas ya logueados: padre, docente, administrador — sin enlace mágico en vivo.
  • Confirmar que /attendance, /reports y /tasks estén habilitados por feature flag para las cuentas demo (FeatureFlagRoleGate).
  • Tener una foto lista en el escritorio para el paso de reporte diario.
  • Tener lista una segunda cuenta de padre para el caso de límite de permisos.
1 · Auth (30 seg)
  1. Mostrar /login una vez, mencionar el enlace mágico, y pasar directo a las pestañas ya autenticadas.
2 · Flujo padre (~3 min)
  1. /feed — señalar las rutas paralelas: novedades personales (@user) vs. grupales (@group) en una sola vista.
  2. /messages → abrir el hilo con el docente del grupo (/messages/[senderID]) → enviar un mensaje en vivo.
  3. Cambiar a la pestaña docente y mostrar el mensaje llegando en tiempo real, sin refrescar.
  4. Volver al padre: abrir un reporte diario desde el feed, mostrar la foto y el botón de descarga en PDF.
3 · Flujo docente (~4 min)
  1. /attendance/[groupId] — marcar entrada de un niño, señalar el contador de presentes en vivo.
  2. /reports/new — publicar un reporte diario (grupal o de un niño), adjuntar la foto, publicar.
  3. Cambiar a la pestaña padre — el nuevo reporte y su notificación aparecen sin refrescar.
  4. /tasks/new — crear una tarea para el grupo.
  5. Marcar salida del niño en /attendance/[groupId] — cierra el ciclo de asistencia.
4 · Flujo administrador (~3 min)
  1. /admin/groups — mostrar un grupo y su docente asignado.
  2. /admin/children o /admin/parents — abrir un registro, mostrar el detalle de perfil.
  3. /admin/teachers → acción de reenviar invitación.
  4. /admin/attendance — vista general de asistencia a nivel administrador.
  5. Mencionar /admin/cleanup (limpieza de adjuntos huérfanos, con vista previa) sin ejecutarla en vivo.
5 · Límite de permisos (~2 min) — el momento de seguridad
  1. En la pestaña padre, mostrar que el ítem de navegación de administrador simplemente no existe.
  2. Con la segunda cuenta de padre, intentar abrir por URL directa el registro de un niño de otra familia — mostrar que la base de datos lo rechaza, no solo la interfaz.
Plan de respaldo: si el Wi-Fi o el staging fallan, tener grabaciones de pantalla de cada flujo — una demo en vivo trabada consume el tiempo de la reunión más rápido que una grabación de una corrida real.
