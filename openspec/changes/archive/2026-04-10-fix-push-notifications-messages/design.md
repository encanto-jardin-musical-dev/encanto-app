## Context

Push notifications for new messages are broken end-to-end. The current implementation has three independent defects that each alone would prevent background notifications from rendering:

1. **SW binding mix-up**: `src/utils/pushNotifications/index.ts` registers `/sw.js` (the Serwist PWA worker) and passes that registration to `getToken()` as `serviceWorkerRegistration`. The Serwist worker in `src/app/sw.ts` has no `onBackgroundMessage` or `push` event handler, so incoming pushes are delivered to a handler-less worker and silently dropped. Meanwhile `public/firebase-messaging-sw.js` (generated by `scripts/generate-firebase-sw.js`) contains the real FCM background handler but is never explicitly registered.
2. **Permission order**: `Notification.requestPermission()` is called *after* `getToken()`. On a fresh install this causes the first token request to fail.
3. **No foreground handler**: `onMessage` is exported from `src/lib/firebase/firebaseConfig.ts` but never called anywhere, so an open tab sees nothing when a push arrives.

Adjacent problems compound the above:

- **Token storage model**: `profiles.fcm_token` is a single-string column, so logging in on a second device overwrites the first. A `subscriptions` table exists with Web Push (VAPID endpoint + p256dh + auth) shape — it is a fossil from an abandoned non-FCM approach and is never written to.
- **Sender path**: The user has a Supabase database webhook named `new_message` on `INSERT` into `messages`, pointed at an Edge Function named `push`. The function lives only in the remote Supabase project; there is no source for it in this repo. The user is not confident it is correctly configured. Even if it were, it would be pushing to a single-token-per-user schema and to a SW that doesn't render notifications.
- **Service account**: A Firebase service-account JSON is available (user confirmed). FCM HTTP v1 is the target API — the legacy server key is deprecated.

Stakeholders: parents and teachers who currently miss conversations because notifications don't arrive; messaging is the product's core value loop.

## Goals / Non-Goals

**Goals:**

- Background push notifications fire reliably for both direct and group messages on all supported browsers that support FCM.
- Users can register multiple devices; each device receives its own push for the same event.
- When the app is open and the user is elsewhere in the UI, a non-intrusive HeroUI toast surfaces the new message. When the user is already viewing the matching thread, nothing extra is shown.
- The Supabase Edge Function `push` lives in this repo at `supabase/functions/push/` and is the source of truth from this change forward.
- The `push` function authenticates against FCM HTTP v1 using a short-lived OAuth token minted from the service account JSON, verifies a shared webhook secret, fans out per recipient device, and self-heals by deleting tokens that FCM reports as invalid.
- `profiles.fcm_token` and the `subscriptions` table are removed; `device_push_tokens` becomes the only token store.
- Logging out from a device removes that device's token row so a shared device stops receiving pushes for the previous user.

**Non-Goals:**

- **Unread count system.** No `messages.read_at`, no `get_unread_message_counts` RPC, no badge UI, no `navigator.setAppBadge` integration. This is a separate proposal.
- In-app notification inbox / history.
- Per-channel notification preferences (quiet hours, mute per conversation, etc.). On/off only.
- Non-message notification types (attendance, daily reports, tasks). Scope is strictly new-message pushes.
- iOS PWA push support guarantees beyond what Safari + FCM already provide.
- Rich notification actions beyond the existing "Open" click.

## Decisions

### D1. New `device_push_tokens` table, not a JSON array on profiles

Chosen: dedicated table `device_push_tokens (id, user_id fk, token text unique, user_agent text, last_seen_at timestamptz, created_at timestamptz)` with an index on `user_id` and a unique constraint on `token`. RLS: users can select/insert/update/delete only their own rows.

**Alternatives considered:**

- *JSON array column on `profiles`*: simpler migration but makes per-token updates (stale cleanup, `last_seen_at`) racy and forces full-row rewrites. Rejected.
- *Reuse `subscriptions` table*: its shape (`endpoint`, `p256dh_key`, `auth_key`) is Web Push VAPID, not FCM. Would require renaming columns and ignoring three of them. Cleaner to drop it and start fresh.

### D2. FCM only, no Web Push fallback

Chosen: delete the `subscriptions` table, FCM is the single strategy (per user confirmation).

**Alternatives considered:** dual-path (FCM for Chromium, Web Push for Safari) — double the surface area, double the bugs, and Safari now supports FCM via the Web Push API it already implements. Not worth it.

### D3. Service worker binding — register `/firebase-messaging-sw.js` explicitly, keep `/sw.js` separate

Chosen: `pushNotifications/index.ts` calls `navigator.serviceWorker.register('/firebase-messaging-sw.js', { scope: '/firebase-cloud-messaging-push-scope' })` and passes that registration to `getToken`. The Serwist SW (`/sw.js`) keeps its root scope `/` for PWA caching and no longer pretends to handle FCM.

**Why different scopes work:** browsers allow multiple service workers on the same origin as long as their scopes do not conflict. Firebase's default scope for its SW is `/firebase-cloud-messaging-push-scope`, which is a sub-path that doesn't overlap with the Serwist SW's `/` scope for navigation/precache purposes. Push events are delivered based on which SW is registered with the PushManager subscription — `getToken` handles that binding when we pass the explicit registration.

**Alternatives considered:**

- *Inline FCM handling into `src/app/sw.ts`*: technically possible (import `firebase/messaging/sw` in the Serwist worker and call `onBackgroundMessage`), but couples PWA caching and push delivery in a single worker. A broken push refactor could break offline navigation. Keeping them isolated is safer.
- *Let Firebase auto-register its default SW*: works, but then we can't pre-register it during the same tick as permission request, and we've already seen timing weirdness (the current `waitForMessaging` polling is a symptom of that). Explicit is better.

### D4. Foreground handling lives in a client provider, not individual pages

Chosen: new `PushNotificationProvider` component mounted in `src/app/providers.tsx` alongside the existing Jotai / HeroUI / React Query providers. It:

1. Calls `onMessage(messaging, payload => ...)` inside a `useEffect`
2. Reads the current pathname via `usePathname()`
3. If the pathname matches the conversation in `payload.data`, no-op
4. Otherwise dispatches a HeroUI toast with the sender name + preview, click handler navigates via `router.push(target)`

**Why a provider not a hook-in-layout:** the handler must exist from first render on any authenticated page, not only when a message component mounts. Providers.tsx is already the global wire-up point.

### D5. Edge Function owned in-repo at `supabase/functions/push/`

Chosen: pull the current remote function via `supabase functions download push`, commit it (verbatim, as a baseline commit) under `supabase/functions/push/`, then rewrite. From this change forward, deploys happen via `supabase functions deploy push` from CI or local. The `new_message` webhook configuration is re-created (or verified) against this function as part of the tasks list.

**Rationale:** the function is currently invisible to code review and version control. Pulling it into the repo is a one-time hygiene cost that unlocks every future change.

### D6. FCM HTTP v1 authentication via service account inside the Edge Function

The Edge Function reads the service-account JSON from a Supabase secret (`FIREBASE_SERVICE_ACCOUNT_JSON`), mints a short-lived OAuth access token using JWT assertion (RS256) against `https://oauth2.googleapis.com/token`, caches it in the function's in-memory scope until expiry (tokens are valid 1 hour), and calls `POST https://fcm.googleapis.com/v1/projects/<project-id>/messages:send` per device.

**Alternatives considered:**

- *Deno npm import of `google-auth-library`*: works in Deno Edge but pulls a large dep graph. A ~40-line hand-rolled JWT signer using Deno's built-in `crypto.subtle` is enough and has no deps.
- *FCM legacy HTTP API with server key*: deprecated by Google, being turned off. Non-starter.

### D7. Per-conversation notification tag + smarter click routing

Background notifications use `tag = 'conversation:<senderId>'` for DMs and `tag = 'conversation:group:<groupId>'` for groups. Multiple pending messages from the same conversation collapse into the latest (intended); pending messages from *different* conversations stack (also intended). Click handler uses `data.route` (set by the Edge Function payload) to focus an existing tab matching that route or open a new window, not the current hardcoded `/`.

### D8. Token lifecycle on login/logout/refresh

- On successful auth + first render in an authenticated session: attempt `storeDeviceToken` (idempotent upsert).
- On `onTokenRefresh` (if exposed) or on detecting a new token via `getToken` returning a value different from the last one cached in `localStorage`: upsert.
- On explicit logout: call `removeDeviceToken` *before* clearing the Supabase session, so the authenticated DELETE actually lands.

**Why a localStorage cache of the last token:** avoids a redundant upsert on every page load; only upserts when the token actually changes or `last_seen_at` is stale (> 24h).

### D9. Webhook secret as shared header

The Supabase database webhook sends a custom header `x-push-webhook-secret: <value>`. The Edge Function compares against `PUSH_WEBHOOK_SECRET` from its secrets. Constant-time comparison.

**Alternatives considered:** HMAC signature over the body (more secure against header leakage) — worth considering but out of scope for a first fix. Documented as future hardening.

## Risks / Trade-offs

- **[R1] Dropping `profiles.fcm_token` is a destructive migration.** Once deployed, an old app build that still writes to that column will fail. → *Mitigation*: ship client changes in the same release as the migration; feature-flag gated rollout is not necessary because the column was already broken for its intended purpose (pushes weren't working anyway), but the migration runs *after* the new client is deployed.
- **[R2] Dual service workers (Serwist + Firebase messaging) on the same origin can be subtle.** Registration order and scope collisions have caused hard-to-reproduce bugs in the wild. → *Mitigation*: explicit scopes, explicit registrations, no reliance on Firebase auto-registration, and manual QA on Chrome, Edge, Safari iOS, and Safari macOS before merge.
- **[R3] Group message fan-out can be expensive** for a teacher broadcasting to a large class (N members × M devices per member). → *Mitigation*: the HTTP v1 API requires one request per token, but these can run in `Promise.allSettled` concurrently. For the current scale (classroom-sized groups) this is fine. If performance becomes a problem, move to FCM topics per group — out of scope here.
- **[R4] Stale-token deletion from the Edge Function writes to the public schema**, which means the function needs a Supabase client configured with the service role key. → *Mitigation*: store `SUPABASE_SERVICE_ROLE_KEY` as a secret alongside the Firebase JSON; document the risk surface; limit the function's DB operations to read `device_push_tokens` / `get_user_groups` and delete by `token`.
- **[R5] The existing remote `push` function may be doing something undocumented** — e.g., writing to another table, calling a third service. Blindly rewriting it could regress something we don't know about. → *Mitigation*: step 1 of the tasks list is to `supabase functions download push` and review the current source before writing the replacement.
- **[R6] Foreground toast timing on route changes** — if a user clicks into `/messages/X` *as* a push for X arrives, the `usePathname` read in the `onMessage` callback might still be the old route. → *Mitigation*: read pathname lazily inside the callback (via a ref updated by a `useEffect` on `pathname`), not captured in the initial closure.
- **[R7] Firebase SDK version drift.** `scripts/generate-firebase-sw.js` hardcodes `firebasejs/10.7.1` while `package.json` carries a newer major version. → *Mitigation*: parameterize the version from the installed `firebase` package version during `prebuild`, or at minimum bump the template to match and add a comment pointing to the script.

## Migration Plan

Deployment order matters because of the destructive schema migration:

1. **Pre-deploy** (manual, before any code ships):
   - `supabase functions download push` to snapshot the current function into `supabase/functions/push/` as the first commit of this change. Review for anything unexpected.
   - `supabase secrets set FIREBASE_SERVICE_ACCOUNT_JSON=...`, `PUSH_WEBHOOK_SECRET=...`, `SUPABASE_SERVICE_ROLE_KEY=...` on the staging project.
2. **Release 1 — client + Edge Function, no schema change yet:**
   - Deploy new client code (still reading/writing `profiles.fcm_token`? No — the client code is rewritten to use `device_push_tokens`, so it needs the table to exist first.)
   - ⚠ Correction: the `device_push_tokens` table must be created **before** the client code deploys, otherwise the new client breaks against the old schema.
3. **Revised order:**
   - **Step 1**: create-only migration — `CREATE TABLE device_push_tokens (...)` with RLS policies. Does not drop anything. Deploy.
   - **Step 2**: deploy new Edge Function `push` (reads from `device_push_tokens`, falls back to reading `profiles.fcm_token` during the transition if present). Verify dispatch end-to-end on staging.
   - **Step 3**: deploy new client code (writes to `device_push_tokens`, stops writing `profiles.fcm_token`). Verify token registration + background + foreground on staging across browsers.
   - **Step 4**: destructive migration — `DROP COLUMN profiles.fcm_token`, `DROP TABLE subscriptions`. Remove the fallback from the Edge Function and redeploy.
   - **Step 5**: regenerate `src/types/database.types.ts`, commit, verify build.
4. **Webhook verification**: regardless of whether the existing `new_message` webhook is well-configured, explicitly reconfigure it under a known spec: `INSERT` on `public.messages`, POST with `x-push-webhook-secret` header, pointed at `https://<project-ref>.functions.supabase.co/push`. Capture the config in a comment in the Edge Function source or a `supabase/README.md`.

**Rollback strategy:**

- Between steps 1 and 4, rollback is trivial — revert client and/or function deploys. The old `profiles.fcm_token` column still exists, old clients still work (they never worked for pushes anyway, but nothing gets worse).
- After step 4, rollback requires restoring the dropped column/table from a point-in-time backup. This is why step 4 happens last, after step 3 has been observed healthy for at least a few hours in production.

## Open Questions

- **Q1.** Does the current remote `push` Edge Function do anything beyond dispatch (e.g., write to an audit log, call Slack, update a "last notified" timestamp)? → *Resolved by task 1.1: download and read the existing function.*
- **Q2.** Does the `messages` table have a stable `group_id` column, or is group membership inferred another way? Need to check schema to write the group fan-out query correctly. → *Resolved by reading `database.types.ts` during task 2.1.*
- **Q3.** What is the exact routing for a group message thread? The DM route is `/messages/<senderId>` (from CLAUDE.md), but the group thread route isn't documented. → *Need to confirm during implementation; if groups don't yet have a dedicated thread route, the notification click falls back to `/messages` list.*
- **Q4.** Should the foreground toast close automatically, and if so after how long? → *Default to HeroUI toast default (~5s); can tune during QA.*
- **Q5.** Safari iOS requires the site to be installed as a PWA to receive push; do we enforce any UI that nudges users to install, or do we silently accept that non-installed iOS users get no push? → *Accepting silently for this change; a PWA install prompt is a separate concern.*
